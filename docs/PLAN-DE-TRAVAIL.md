# Cadence — Plan de travail : corrections et améliorations

> Rédigé le 9 novembre 2026, après l'audit complet du système.
> Cadence = le projet de la conversation « Asana avec IA embarquée ».
> Dépôt : https://github.com/JonathanMUBAKE/cadence — branche de référence : `main`.

Ce document est la feuille de route partagée par **tous les agents** qui travaillent sur Cadence
(session cloud et session sur l'ordinateur). Il dit quoi faire, dans quel ordre, où, et comment
vérifier que c'est fait. Cochez les cases au fil de l'eau et commitez ce fichier avec le travail.

---

## 0. Règles de travail (à lire avant tout)

1. **Toujours partir de la dernière version** : `git fetch origin && git checkout main && git pull`.
2. **Une branche par lot** : `lot-a-securite`, `lot-b-robustesse`, `lot-c-console`… Jamais de travail direct sur `main`.
3. **Tests d'abord** (TDD) : écrire le test qui échoue, puis le code. Chaque lot ajoute ses tests dans `server/src/*.test.ts`.
4. **Avant chaque commit** : `npm run typecheck` et `npm test` doivent passer (51 tests aujourd'hui, ce nombre ne doit jamais baisser).
5. **Vérifier dans un navigateur** toute modification d'interface (`npm run build && npm start`, puis http://localhost:4000).
6. **Pousser** la branche sur `origin`, puis noter dans la section « Journal » en bas de ce fichier ce qui a été fait.
7. **Langue** : interface, messages d'erreur et commits en français.
8. **Ne jamais commiter** de secret (clé API, mot de passe) : ils vont dans `.env` (ignoré par git).

Commandes utiles : `npm install` · `npm run build` · `npm start` · `npm run dev` (rechargement à chaud) ·
`npm test` · `npm run typecheck` · `npm run e2e`.

## 3. Lots de travail, dans l'ordre

### Lot A — Sécurité bloquante (avant toute mise en ligne)

Objectif : plus personne ne peut se connecter à la place d'un autre ni lister les utilisateurs.

- [x] **A1. Vraie authentification par e-mail + mot de passe** (corrige E1)
  - Migration `004_authentification.sql` : colonne `users.password_hash`, table `sessions` (id, user_id, created_at, expires_at, ip, user_agent, revoked_at), table `login_attempts`.
  - Hachage **argon2id** (paquet `@node-rs/argon2`) ou `crypto.scrypt` natif si on veut zéro dépendance native.
  - `POST /api/auth/login {email, password}` ; message d'erreur unique « E-mail ou mot de passe incorrect » (ne pas révéler si l'e-mail existe).
  - Cookie de session = identifiant de session opaque (plus l'id utilisateur), `httpOnly`, `sameSite=lax`, `secure` en production ; déconnexion = révocation en base.
  - Les coéquipiers IA n'ont jamais de mot de passe et ne peuvent pas se connecter.
  - **Mode démo conservé** derrière `CADENCE_DEMO=1` (choix d'un profil), désactivé par défaut en production.
  - Données de démo : mot de passe commun documenté dans le README (ex. `cadence-demo`).
  - Tests : connexion OK, mauvais mot de passe → 401, IA → refus, session révoquée → 401, cookie forgé → 401.
- [x] **A2. Fermer la liste publique des utilisateurs** (corrige E2)
  - Supprimer `GET /api/auth/users` hors mode démo ; page de connexion = formulaire e-mail + mot de passe.
  - Test : `GET /api/auth/users` → 404 quand `CADENCE_DEMO` n'est pas actif.
- [ ] **A3. Limitation de débit et en-têtes** (corrige E3)
  - `@fastify/rate-limit` : 10 tentatives de connexion / 15 min par IP et par e-mail ; 300 requêtes / min par session sur l'API.
  - `@fastify/helmet` : CSP adaptée à l'interface Vite, `X-Content-Type-Options`, `Referrer-Policy`, HSTS en production.
  - Protection CSRF : vérifier l'en-tête `Origin` sur les requêtes qui modifient (POST/PUT/PATCH/DELETE).
- [x] **A4. Secrets obligatoires en production** (corrige E4)
  - Si `NODE_ENV=production` et que `COOKIE_SECRET` ou `CADENCE_SECRET_KEY` manque ou fait moins de 32 caractères → refuser de démarrer avec un message clair.
  - Documenter dans `.env.example` et le README.
- [x] **A5. Mot de passe oublié** (utilise la messagerie existante)
  - Lien à usage unique valable 30 min, envoyé depuis `contact@<domaine>` de l'organisation (ou SMTP plateforme, voir Lot C).

### Lot S — Séparation des droits d'accès : chacun n'accède qu'à ce qui lui est destiné (planifié le 19/11/2026)

Demande de l'utilisateur (18/11/2026) : séparer les droits d'accès de tout le monde selon une logique claire, pour que
chacun n'accède qu'à ce qui lui est destiné. L'authentification (mots de passe, double authentification, SSO) vient
plus tard et n'est pas dans ce lot.

**Point de départ.** Les lots 3, 7, 10 à 14 ont déjà posé l'essentiel :
- 13 profils (Propriétaire, Administrateur, Membre, Invité, Lecture seule, Agent, Stagiaire, Consultant,
  Chef d'entité, DGA, DG, Assistant(e) de direction, Responsable informatique) et 58 droits ;
- la règle « ce qui le concerne » (`svc.scopeOf`), la matrice de toutes les routes (`matrice.test.ts`) ;
- les corrections des agents testeurs (lot 14).

Ce qui manque, c'est une règle unique, écrite, appliquée partout et vérifiée profil par profil, plutôt qu'une
décision prise module par module.

**Principes (à valider avec l'utilisateur avant le code).**
1. *Besoin d'en connaître* : on lit ce qu'on porte (ses tâches, ses dossiers, son dossier RH), ce que dirige son
   entité (et ses entités rattachées), et ce à quoi on est convié. Le reste n'existe pas pour soi (404, pas 403).
2. *Trois périmètres seulement* : **soi**, **son entité** (et en dessous), **l'institution** (pilotage de la DG et
   son cabinet). Chaque lecture et chaque écriture déclare son périmètre.
3. *Séparation des fonctions* : piloter (DG, DGA, cabinet), administrer la plateforme (responsable informatique),
   gérer les personnes (RH) sont trois fonctions distinctes ; aucune ne donne accès aux données des deux autres.
4. *Confidentiel avant tout* : une fiche, une réunion, un document, un projet marqué confidentiel ou privé ne sort
   de son cercle ni par une liste, ni par une recherche, ni par un message d'erreur, ni par un export.
5. *Champs sensibles* : montants (contrats, budgets, finance des accords), données personnelles (RH), notes RH,
   évaluations ; ils se masquent par fonction même quand l'objet est lisible.
6. *L'IA lit avec les droits de qui la lance*, jamais plus, et n'agit jamais comme une personne.
7. *Contrôle serveur, journal, test* : chaque règle est contrôlée côté serveur, chaque accès sensible journalisé,
   chaque règle couverte par un test qui rejoue le contournement.

**Étapes de mise en œuvre.**
1. *Inventaire automatique* : un script parcourt toutes les routes et produit, pour chacune, le droit exigé et le
   périmètre appliqué ; il signale les routes sans périmètre (cible : zéro).
2. *Un seul garde de périmètre* : généraliser `scopeOf` en un garde commun (`assertScope(actor, objet)`) utilisé par
   tous les modules ; supprimer les variantes locales.
3. *Points restants du lot 14* : budgets du portefeuille masqués aux agents non membres (C-M8) ; un projet porté par
   une entité reste lisible de son chef (C-M9) ; fiche partenaire limitée aux accords du périmètre (P-M4) ; recherche
   globale passée au même filtre, étendue aux partenaires et accords.
4. *Champs sensibles* : une fonction unique de masquage par fonction (montants, données personnelles, notes RH),
   appliquée aux réponses de l'API et aux exports.
5. *Matrice des profils* : étendre `matrice.test.ts` à chaque profil métier (agent, chef, cabinet, DG, RH,
   informatique) et à chaque route, avec le résultat attendu ; toute route nouvelle sans ligne fait échouer la suite.
6. *Interface* : n'afficher que ce qui est accessible (menus, boutons, onglets) à partir de la même matrice.
7. *Agents testeurs* : relancer les quatre agents testeurs sur la démo à la fin du lot ; zéro anomalie haute.

**Décisions de l'utilisateur (19/11/2026).**
- **La DG lit tout, mais ne fait pas tout** : lecture de l'ensemble, notes RH et évaluations comprises ; ses actions restent celles de sa fonction (trancher, confirmer, signer, approuver), pas celles des RH, de l'administration ou des chargés.
- **Le cabinet voit la même chose que la DG** (lecture), montants compris ; il prépare, il ne tranche ni ne confirme.
- **Les comptes rendus du comité de direction sont lisibles des chefs d'entité.**
- **Annuaire** : complet pour tous, limité aux informations professionnelles (nom, fonction, entité, adresse professionnelle) ; les données personnelles restent au dossier RH.

**Politique d'accès retenue (19/11/2026, demandée par l'utilisateur : « la meilleure »).** Le modèle de référence est
celui de l'administration canadienne (Politique sur la sécurité du gouvernement : *besoin de savoir*, renseignements
protégés, accès consignés), le plus opérationnel des trois et rédigé en français. Il est complété par la protection
des données personnelles à l'européenne (minimisation, finalité) pour les dossiers des agents, et par le référentiel
américain NIST SP 800-53 comme liste de contrôles techniques (moindre privilège, séparation des fonctions, journal).
Concrètement :
- *Contrôle hiérarchique admis, mais jamais invisible* : un chef ou la DG lit un projet privé de son périmètre ; la
  lecture entre au journal du projet (« Projet privé consulté par la hiérarchie »). La consultation d'un dossier RH par
  un tiers était déjà tracée.
- *Catégories protégées*, fermées même à la hiérarchie et réservées à la personne concernée et à qui traite le dossier :
  santé (congés de maladie : le chef et la DG voient « Absence » et les dates, pas la nature ni le motif) ; et, pour les
  modules à venir, procédures disciplinaires, plaintes et signalements, travaux d'audit interne en cours.
- *Point de fond relevé* : la DG de la démonstration a le rôle « propriétaire » de l'institution, qui ouvre les 58 droits
  (gestion RH comprise). Cela contredit « la DG lit tout, mais ne fait pas tout ». Les catégories protégées s'appuient
  déjà sur la fonction (profil ou droit accordé), pas sur ce rôle. **Traité le 19/11/2026** (décision de l'utilisateur :
  « Oui, sépare ») : le niveau « Propriétaire » n'ouvre tous les droits qu'avec le profil système du même nom ; une
  personne propriétaire qui tient un profil de fonction n'a que ses droits, et n'administre plus tous les projets. Dans
  la démonstration, la propriété technique revient au responsable informatique (27 droits, aucun accès au pilotage) et
  la DG tient sa fonction par son profil (niveau administrateur, 52 droits, sans RH ni profils). Contrôle croisé :
  personne ne s'accorde de droit ni ne change son propre profil, pas même le propriétaire ; tout droit sensible accordé
  est signalé aussitôt à qui relit le journal de l'administration (la DG). Les dossiers RH de la démonstration sont
  tenus par le service RH, avec une seconde gestionnaire pour le dossier de la cheffe. Tests : `server/src/proprietaire.test.ts`.

**Fait (lot S, première partie, 19/11/2026)** : menu limité à ce qui concerne chacun ; plans et partenaires limités au périmètre (la liste de choix des formulaires reste complète) ; comptes rendus du comité de direction lisibles des chefs ; budgets des projets réservés à la direction, au cabinet, aux chefs de l'entité porteuse et aux membres ; projet d'entité lisible de ses chefs même privé ; fiche partenaire limitée aux accords du périmètre. Tests : `server/src/lot-s.test.ts`. Restent les étapes 1 (inventaire automatique), 2 (garde unique), 5 (matrice par profil métier) et 7 (nouvelle passe des agents testeurs).

> direction, Chef d'entité, DG, Responsable informatique, profils démunis). Leurs constats, puis les
> décisions de modèle prises avec Jonathan les 24 et 25 novembre, donnent les lots ci-dessous.
> **L'ordre est celui du rapport effet/coût**, sauf le lot T qui conditionne tous les autres.

### Lot T — Les fonctionnalités sont des briques (principe, à poser avant le reste)

Une fonctionnalité s'écrit **une fois** et s'appelle là où on en a besoin. Un composant « tâche » se
comporte de la même façon à l'accueil, dans un projet, dans « Mon entité », au courrier et dans une
réunion. Il n'affiche pas forcément les mêmes données : ce qui varie, c'est **le niveau d'accès de la
personne** et **le module où la brique est posée** — jamais le comportement, jamais une réécriture.

- [ ] **T1.** Écrire la règle dans `docs/DESIGN-SYSTEM.md` : toute fonctionnalité réutilisée est une brique
      paramétrée par le contexte (module) et par les droits, jamais recopiée.
- [ ] **T2.** La brique « tâche » : un seul composant de ligne, un seul tiroir, un seul formulaire de
      création, quels que soient l'écran et l'origine (projet, entité, réunion, courrier, décision).
- [ ] **T3.** Inventaire et suppression des doublons déjà repérés : trois composants `Card` locaux qui
      refont `Section` (`pages/Pilotage.tsx`, `pages/Account.tsx`, `components/unit-dashboard.tsx`), deux
      implémentations de grille de mois, deux formulaires d'arrivée d'une personne (`/admin` et `/org`).
- [ ] **T4.** Une brique « ce qu'on me demande » : une seule liste des charges d'une personne, quelle que
      soit l'origine — tâche de projet, action de réunion, courrier pour traitement, décision à exécuter.

**La règle vaut pour tous les composants, pas seulement la tâche** (demandé le 25 novembre). Un bouton a
partout la même taille et le même type ; seule l'**accentuation** change selon l'insistance de l'action.
Un champ, un tableau, une pastille, un dialogue se comportent de la même façon dans tous les modules.
Les briques existent déjà : `Button`, `IconButton`, `Checkbox`, `Dialog`, `ConfirmDialog`, `Empty`, `Menu`,
`Chip`, `Avatar` dans `components/ui.tsx` ; `Field`, `Input`, `Select`, `Textarea` dans `components/gov.tsx` ;
`DataTable` et `GroupedTable` dans `components/collection.tsx`. Elles sont contournées :

- [ ] **T5. Les boutons.** 148 balises `<button>` sont écrites à la main, dont 4 seulement dans `ui.tsx` —
      donc **144 boutons hors de la brique**. Et **100 hauteurs** sont posées à la main (`h-8`, `h-9`,
      `h-10`…) alors que `Button` a trois tailles. Le composant partagé, lui, n'est appelé qu'avec quatre
      variantes (138 `primary`, 23 `ghost`, 13 `danger`, 8 `ai`) et deux tailles (120 `sm`, 6 `lg`) : la
      palette d'accentuation est donc déjà la bonne, c'est son emploi qui ne l'est pas.
- [ ] **T6. Les champs.** 91 `<input>`, 26 `<select>` et 20 `<textarea>` écrits à la main, alors que
      `Field`, `Input`, `Select` et `Textarea` existent et portent le libellé permanent, le halo de focus et
      l'erreur sous le champ (règles 5.4 du système de design).
- [ ] **T7. Les tableaux.** 10 `<table>` à la main contre 8 appels de `DataTable` / `GroupedTable` : un
      tableau sur deux ignore la sélection, le tri, les actions de ligne et la pagination de la maison.
- [ ] **T8.** Une fois les briques rétablies, interdire la régression : un test qui échoue si une balise
      `<button>`, `<input>`, `<select>` ou `<textarea>` apparaît ailleurs que dans les fichiers de briques,
      sur le modèle de `server/src/droits-interface.test.ts`.

### Lot X — Le courrier, entrant et sortant

Le plus gros lot. Le modèle a été repris avec Jonathan le 25 novembre.

- [ ] **X1. Un seul enregistrement.** Aujourd'hui le courrier est enregistré trois fois sur papier (service
      courrier, secrétariat, antichambre). Dans l'outil : une seule entrée, à la réception.
- [ ] **X2. Un état par personne et par entité.** Le courrier ne porte aujourd'hui qu'un `assignee_id`, au
      singulier. Il faut que le même courrier soit, au même moment, *à dispatcher* pour le secrétariat,
      *à transmettre* pour l'antichambre, *pour lecture* pour les uns et *pour traitement* pour les autres.
- [ ] **X3. Deux mentions : « Pour traitement » et « Pour information »**, cumulables sur une même personne.
      (L'usage français dit « pour attribution » ; écarté tant que « Attributions » désigne autre chose.)
- [ ] **X4. Un courrier pour traitement crée une tâche** liée au courrier, avec son échéance — même brique
      que les actions de réunion (voir T4).
- [ ] **X5. L'étiquette et l'accusé de réception** : une étiquette imprimable à coller sur le document,
      portant le numéro et les informations d'enregistrement. Rien de tel n'existe.
- [ ] **X6. Le circuit passe par le signataire** : un courrier n'y entre jamais aujourd'hui. L'annotation de
      la DG sur un entrant, et le projet de réponse sortant, empruntent le même chemin — visa, puis signature.
- [ ] **X7. Deux phases pour le sortant** : préparation (l'auteur et l'antichambre écrivent) puis signature
      (texte figé). Sans cela, la garantie « contenu intact depuis l'entrée dans le circuit » ne vaut plus rien.
- [ ] **X8. La DG seule engage l'Agence**, le DGA en intérim. Or `signature.institution` n'appartient qu'au
      profil DG et aucune délégation n'existe : il faudrait donner le droit au DGA et penser à le reprendre.
      Prévoir une délégation datée, qui s'ouvre et se ferme seule.
- [ ] **X9. Les modèles de courrier** : aucun n'existe. Déposer un modèle (en-têtes compris), la personne
      saisit, le système génère ; la finalisation — numéros, impression — revient au secrétariat.
- [ ] **X10. La numérotation** (donnée par Jonathan le 25 novembre 2026). Quatre chiffres, `0001`, puis
      `0002`, et ainsi de suite : le rang suit simplement le nombre de courriers, à l'entrée comme à la
      sortie. Le premier courrier du 1er janvier de l'exercice porte `0001`, et **le compteur se
      réinitialise tout seul au changement d'année**. Entre deux rangs on peut insérer un **numéro
      secondaire** : `0001A`, `0001B`. Aujourd'hui `ENT/2026/0142` est **calculé** (sens, année, rang) et
      n'admet aucun suffixe : il faut un numéro principal stocké et un suffixe à côté.
- [ ] **X11. Un calendrier embarqué, qui marche hors ligne.** Le système doit savoir seul qu'un mois ou une
      année a commencé, avec ou sans connexion. Jonathan demande d'embarquer le calendrier jusqu'en 2099.
      **Les deux vraies difficultés sont ailleurs, et il ne faut pas les coder à moitié :**
      *(a)* **l'horloge**, pas le calendrier — l'arithmétique des dates jusqu'en 2099 tient en quelques
      lignes, mais la date d'un poste hors ligne peut être fausse ou reculée ; il faut donc une horloge de
      référence conservée par le serveur, qui n'avance jamais à rebours, et qui se recale à la reconnexion
      en journalisant l'écart ;
      *(b)* **l'unicité du rang** quand plusieurs postes enregistrent hors ligne : deux courriers ne doivent
      pas repartir avec le même `0007`. Soit le rang n'est attribué qu'au serveur, et un courrier saisi hors
      ligne porte un numéro provisoire jusqu'à la synchronisation, soit chaque poste tient une plage
      réservée. À trancher avant d'écrire la moindre ligne.
- [ ] **X11. Antidater** est déjà permis et parfaitement silencieux (seule une date future est refusée). Cela
      doit alerter à la saisie et entrer au journal.
- [ ] **X12. Les archives** : un seul registre, où chaque courrier porte qui l'a classé et à quel dossier il
      se rattache. Les trois archives citées (secrétariat, DG, par projet) en sont trois vues.
- [ ] **X13. Les rappels** : tous les deux jours, et « en retard » au bout d'une semaine. Aujourd'hui un seul
      rappel part, et seulement une fois l'échéance atteinte ; l'escalade au chef d'entité se produit une fois.
- [ ] **X14.** « Répondre » n'existe pas sur un courrier entrant ; le registre n'a ni recherche ni filtre ;
      ses cinq compteurs ne sont pas cliquables ; il n'y a pas d'« Enregistrer et suivant ».
- [ ] **X15.** Les annexes (limite de l'ordre de 3 Mo, ou un espace externe) : **remis à plus tard par Jonathan.**

### Lot AD — Logique qui ne tient pas, dans les cinq modules restants

Relevé le 25 novembre par lecture du code, sur les modules que la campagne des testeurs n'avait pas
parcourus : partenaires et conventions, congés, ressources humaines, portefeuille et activités,
coéquipiers IA. Les deux premiers points ont été revérifiés à la main.

- [ ] **AD1. Le secret médical sort par les notifications.** Le masque (`leaves.ts:94-100`) ne s'applique
      qu'à `get`, `list` et `summary` : il remplace « maladie » par « absence » et vide le motif, et le
      commentaire du code dit l'intention — « la DG voit l'absence, pas la maladie ». Mais l'avis au chef
      (`leaves.ts:296-303`) écrit le type de congé dans son titre et **le motif en clair dans son corps** ;
      `decide()` (335-349) renvoie la ligne non masquée ; `notifyInterim` (309-318) nomme le type à
      l'intérimaire. L'avis reste ensuite dans leur centre de notifications. **Règle serveur.**
- [ ] **AD2. Les raisons budgétaires fuient par une route voisine.** `review()` (`portfolio.ts:198-202`)
      retire les montants et les raisons commençant par « budget » pour qui n'a pas le droit de les voir ;
      `health()` (227-236) renvoie `reasons` tel quel à tout lecteur du projet — dont « budget consommé à
      125 % ». **Règle serveur** : un seul masque appelé par les deux routes.
- [ ] **AD3. La création d'un agent enrôle avant de valider.** `hr.ts:344` ouvre le compte, envoie le lien
      et prévient les administrateurs ; les contrôles (date de fin obligatoire, dossier déjà existant)
      viennent après, en 378-380. Un contractuel saisi sans date de fin laisse un compte créé, une personne
      membre sans dossier, et un nouvel essai qui échoue sur une adresse déjà prise. **Règle serveur.**
- [ ] **AD4. Un avenant signé pendant la résiliation de son accord reste bloqué pour toujours.**
      `terminate()` (`agreements.ts:780-810`) ignore les avenants en cours ; à la signature,
      `assertParentLive` (569-574) lève un 409. L'avenant ne peut plus ni entrer en vigueur, ni être
      supprimé, ni rejeté — et la DG a signé un acte sans effet. **Règle serveur.**
- [ ] **AD5. La sortie d'un agent ne se défait pas et laisse ses demandes ouvertes.** Une seule route, qui
      lève 409 si la date est déjà posée ; aucune annulation. `applyExit` suspend le compte et coupe les
      sessions mais ne touche pas à `agent_leaves` : le chef continue de recevoir à valider les congés d'un
      agent parti, qui reste intérimaire d'autres personnes. **Règle serveur.**
- [ ] **AD6. Les congés sont validés moins bien qu'ailleurs.** `leaves.ts:40` n'a qu'une expression
      régulière là où le reste du serveur emploie `isRealDate` : « 2026-02-31 » atteint la base et finit en
      500. `workingDays` boucle sans borne et ignore les jours fériés. Une demande du samedi au dimanche
      donne 0 jour et passe. Aucun plafond de solde. **Règle serveur.**
- [ ] **AD7. Modifier une activité n'est pas journalisé** — y compris lever sa confidentialité ou changer
      son responsable (`activities.ts:248-288`). Seuls `create` et `remove` laissent une trace. L'Agence ne
      peut pas répondre à « qui a ouvert ce dossier confidentiel ». **Règle serveur.**
- [ ] **AD8. Une règle IA garde les droits de son premier auteur.** `saveRule` (`ai/engine.ts:880-936`) ne
      journalise rien et ne change pas `created_by` ; `ruleMayRun` ne vérifie que les droits de celui-ci. Un
      administrateur de projet sans droit de déléguer peut réécrire la consigne, et l'IA agira sous les
      droits d'un autre. **Règle serveur.**
- [ ] **AD9. Une proposition de l'IA sans décideur attend indéfiniment** et verrouille la tâche :
      `checkpoint` (`ai/engine.ts:590-641`) attend sans délai, et si la liste des approbateurs est vide,
      personne n'est prévenu. `start()` refuse ensuite toute intervention sur cette tâche, en silence.
      **Refonte d'un parcours.**
- [ ] **AD10. Une validation humaine peut être journalisée « approuvée » sans que rien ne s'exécute.**
      `decide()` (`ai/engine.ts:672-710`) passe la ligne à `approved` et journalise, puis, si l'attente
      n'existe plus, la marque `expired` et répond 200. Pour un acte opposable, la trace ment.
      **Règle serveur** : refuser la décision avant tout journal.
- [ ] **AD11. La liste des exécutions IA est tronquée avant d'être filtrée par droits** (`listRuns`,
      `ai/engine.ts:978-998`) : un agent peut ne rien voir parce que les cinquante dernières appartiennent à
      d'autres projets. **Règle serveur.**
- [ ] **AD12. Une demande d'arbitrage part à tous les détenteurs de `decisions.record`**, avec le nom du
      dossier et la question, sans regarder qui a le droit de l'ouvrir (`portfolio.ts:293-307`). Et si le
      demandeur est le seul décideur, l'arbitrage reste en attente. **Règle serveur.**
- [ ] **AD13. La fusion de deux partenaires contourne la règle des accords en vigueur** : `setState` refuse
      de clore une fiche qui en porte un, `merge` (`partners.ts:804-888`) y transfère les accords sans
      regarder l'état de la fiche gardée. **Règle serveur.**
- [ ] **AD14. Une demande de congé peut n'avoir personne pour la décider** : l'approbateur est figé à la
      création et n'est jamais recalculé ; sans chef, et si le demandeur est le seul gestionnaire RH, la
      demande attend pour toujours. **Règle serveur.**
- [ ] **AD15. On peut confier une suite à quelqu'un qui ne peut pas ouvrir l'activité** : l'avis porte le
      titre, et le lien répond « introuvable » (`activities.ts:297-318` contre `readable()`, 93-108).
      **Règle serveur et retouche d'écran.**
